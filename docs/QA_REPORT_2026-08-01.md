## 2. What was found, and how

Everything below was verified by running it, not by reading code. Where a claim
could not be verified, it says so.

### 2.1 Any logged-in user could read the clinic's finances

Probed with three low-privilege roles against ten module URLs:

```
BEFORE   groomer    can open: /finance/, /accounting/, /inventory/, /procurement/, /crm/owners
         reception  can open: /finance/, /accounting/, /inventory/, /procurement/, /crm/owners
         nurse      can open: /finance/, /accounting/, /inventory/, /procurement/, /crm/owners

AFTER    groomer    can open: /crm/owners
         reception  can open: /finance/, /crm/owners      (reception bills — correct)
         nurse      can open: /crm/owners
```

**Root cause:** 271 of 376 routes carried only `@login_required`, with no role gate
at all. The permission machinery to stop this existed and governed nothing —
`@permission_required` appeared on **zero** routes; its only occurrence in the
codebase was inside its own docstring. Every role shipped with
`permissions_json='[]'`, read as "no data, fall open".

**Why that is worse than having no permissions screen:** an administrator who
unticked "Invoicing" for reception saw the change saved, and reception kept full
access. The screen told the person responsible for access control that they had
restricted something they had not.

**Fixed at** `login_required` — the one gate all 376 routes pass through — rather
than by hand-adding role lists to 271 routes, where some would have been missed.
Ships with a default grant per role, filling only roles that have none, so an
administrator's own configuration is never overwritten.

### 2.2 The public API could not be rate limited, at any volume

`_check_rate_limit` called `is_rate_limited(ip)`, which counts rows in
`login_attempts` — a table only `record_failed_login` writes, and nothing in the
public API touches. The counter the guard read stayed empty for public traffic.

These endpoints are unauthenticated, create owners, pets and appointments, and
send WhatsApp messages.

Now `sec.throttle()` records the hit it is checking. Its own table, so login is
undisturbed; per-bucket, so a burst of contact forms cannot close the booking form
for someone with a sick animal.

### 2.3 There was no payment record at all

`models.database.add_payment` accepted `method`, `reference` and `received_by` and
**discarded all three**. It never wrote to the `payments` table — it only
incremented `invoices.paid_amount`. Its docstring blamed a table belonging to a
different product, which had long since stopped being true.

So the system could say an invoice was paid and could not say **by whom, when, or
how**. No record of a failed attempt. No refund. Nothing preventing a
double-clicked button charging twice.

### 2.4 Smaller findings, each verified

| Finding | Consequence |
|---|---|
| Request by IP resolved to a tenant named `127` | Every health check and load-balancer probe would 404 |
| Five modules built tables behind a plain `if _ready` boolean | Every clinic after the first would have no `login_attempts` — rate limiting dead |
| The TTL cache was one dict shared by all clinics | One clinic seeing another's name, logo and tagline |
| Excel export tested `isinstance(v, (int, float))` | On PostgreSQL the TOTAL row silently skips every money column |
| `sum()` on mixed Decimal/float | Financial exports 500 during the NUMERIC cutover |
| "Insurance" had no gateway | An insurer settlement recorded as **cash** — money looked for in a drawer it was never in |
| Overpayment was silently clamped | 1000 taken against a 250 invoice recorded 250 and discarded 750 |

## 3. Payments

**Cash is the primary method** — first in the list, needs no configuration, keeps
working when the internet does not.

Architecture: `Gateway` interface → `payment_intents` (one row per *attempt*,
including failures) → `payments` (the ledger: money that actually arrived) →
`payment_events` (append-only history). Intents and ledger are deliberately
separate; collapsing them means either recording money that never arrived, or
losing the evidence of what went wrong.

The five cases you named, each with a test:

| Case | Behaviour | Test |
|---|---|---|
| **Duplicate** | `idempotency_key` UNIQUE; a repeat returns the first attempt | `test_the_same_payment_cannot_be_taken_twice` |
| **Failure** | Recorded with a reason; ledger untouched; invoice stays Unpaid | `test_a_failed_payment_is_recorded_and_pays_nothing` |
| **Refund** | Negative ledger row, never an edited one; invoice recomputed | `test_a_refund_reverses_the_invoice_and_leaves_both_rows` |
| **Cancellation** | Pending only; a captured payment must be refunded instead | `test_a_captured_payment_cannot_be_cancelled` |
| **Retry** | Capture is idempotent; replayed callbacks are no-ops | `test_a_REPLAYED_callback_does_not_pay_the_invoice_twice` |

`invoices.paid_amount` is now **derived by summing the ledger**, not incremented.
An incrementing total drifts from reality the first time anything is refunded or
replayed.

### Online gateway: Paymob

Chosen because it is what an Egyptian clinic can actually use — local cards,
mobile wallets, Fawry, instalments, settlement to an Egyptian bank account, and a
**free sandbox with no upfront cost**. Stripe does not onboard Egyptian entities
for payouts.

**NOT VERIFIED AGAINST THE SANDBOX.** There is no Paymob account yet. Two items are
marked `TODO(sandbox)` in the code and need one real transaction to confirm:

1. the exact field set and ordering the HMAC is computed over
2. the Authorization scheme on the intention call

Both fail **closed**: a wrong HMAC field list rejects genuine callbacks rather than
accepting forged ones. The failure mode is "online payments do not complete", never
"anyone can mark invoices paid".

The callback endpoint exists and is tested (10 tests) — without it the online flow
could never finish and the gateway would be decorative.

Adding a gateway: subclass `Gateway`, implement three methods, register it. It then
appears in the UI automatically — the invoice screen is driven by the registry, not
a hardcoded list.

## 5. Deliberately not done, with reasons

**The `NUMERIC(12,2)` money migration was NOT applied.** This is a considered
decision, not an omission. `docs/MONEY_PRECISION.md` prescribes the order: make the
application Decimal-safe **first**, change column types at the PostgreSQL cutover.
None of the three prerequisites existed. Applying the migration now would mean that
on PostgreSQL every amount becomes a `Decimal`, `jsonify` raises, mixed
`float + Decimal` arithmetic raises — and, in that document's own words, *"your
tests will pass and production can still break."*

What was done instead: the prerequisites, plus `tests/test_money_decimal_safety.py`,
which feeds `Decimal` values through the money paths **on SQLite**, making the
engine divergence testable before the migration rather than after. Those tests are
the gate on applying it.

**Delivery, drivers, riders, maps** — not built. These do not exist in this
application; it is a clinic management system. Building them is a second product,
not a fix. Confirmed by search: zero files for driver, rider, courier, transport,
geocode, latitude/longitude.

## 6. What still stands between this and production

1. **No clinic has ever used it.** No amount of testing substitutes. One pilot is
   worth more than the next 500 tests.
2. **Paymob is unverified.** Needs an account and one sandbox transaction.
3. **Money is still binary float** in 64 columns. Migration written and tested,
   held for the PostgreSQL cutover per §5.

Also open, lower severity: telemedicine sessions carry no `visit_id` (a remote
consultation bills and prescribes but never joins the animal's history); retail
`ps_products` and clinical `stock_batches` are unlinked ledgers.

## 8. Honest note on method

Three times this session my own tests corrected my design, and each correction is
recorded in the commit that made it:

- Letting a module grant **replace** a route's role list handed every receptionist
  the destructive routes. `test_template_delete_is_role_gated` put it plainly: *"a
  receptionist deleted a template."* Grants now narrow, never widen.
- Gating self-service behind the module grant locked every employee out of their
  own payslip and timesheet. Five tests named it.
- The throttle's fail-open guard did not cover `get_db()`, so it failed closed. Its
  own test caught it.

A design that survives its own test suite arguing with it is worth more than one
that was never argued with.
