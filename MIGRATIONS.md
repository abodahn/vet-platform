# Database Migrations

Alembic lives in `db_migrations/`. (The unrelated `migrations/` directory holds
`excel_import.py` for legacy Excel imports — nothing to do with schema.)

All commands are run **from the platform root** (`D:\vet\platform` on this
machine — nothing here hardcodes that path) and always with an explicit `-c`:

```
alembic -c db_migrations/alembic.ini <command>
```

Alembic is not yet in `requirements.txt`. Add:

```
alembic>=1.13.0
```

---

## Which database do I hit?

`db_migrations/env.py` resolves the URL with the *same* rules `app.create_app()`
uses, in this order:

1. `POSTGRES_DSN`, **if** it matches `postgresql://user:pass@host:port/dbname`
   (app.py applies exactly this regex; a malformed DSN silently falls back to
   SQLite, and alembic mirrors that so the two can never disagree).
2. `PLATFORM_DB_PATH`
3. `<platform>/data/platform.db`

No URL and no credentials are stored in `alembic.ini`. Set the environment the
same way you set it for the app, then run alembic.

Check before you act:

```
alembic -c db_migrations/alembic.ini current      # which revision this DB is at
alembic -c db_migrations/alembic.ini history      # what revisions exist
```

`current` printing nothing means the database has never been stamped.

## Stamping the existing production database (do this once)

Production already has the baseline schema — it was built by `init_db()`.
`upgrade` would try to re-create it. Use `stamp`, which writes the version row
and **executes no DDL at all**:

```
# PowerShell, on the production host
$env:POSTGRES_DSN = "postgresql://USER:PASS@HOST:5432/DBNAME"
alembic -c db_migrations/alembic.ini stamp 0001_baseline
alembic -c db_migrations/alembic.ini current      # expect: 0001_baseline (head)
```

That creates one new table, `alembic_version`, holding a single row. Nothing
else in the database is read or written. Verified on a throwaway SQLite copy:
the set of tables, indexes and columns was byte-identical before and after.

Do **not** run `alembic upgrade head` against a database that already has the
schema. Take a backup first regardless (`platform/backups/`).

## There are deliberately TWO heads — `upgrade head` will error

```
alembic -c db_migrations/alembic.ini heads
0002_audit_log_indexes (head)
0002_money_numeric (head)
```

Both are children of `0001_baseline`. They are independent branches that touch
disjoint tables and are **not** meant to be applied together, so `upgrade head`
is ambiguous and fails:

```
FAILED: Multiple head revisions are present for given argument 'head'
```

That error is the feature, not a defect to work around. It stops someone
reaching for a cheap index from applying a deferred financial data migration by
accident. Name the revision you want:

| Revision | What it does | Status |
|---|---|---|
| `0002_audit_log_indexes` | Adds 5 indexes to `audit_log` (timestamp, username, module, entity_type+entity_id, action). Additive, idempotent, no data touched. | **Safe to apply.** |
| `0002_money_numeric` | Retypes 34 money columns `REAL` → `NUMERIC(12,2)`. | **ON HOLD** — prepared artefact only. ~550–800 call sites of blast radius and 172 `float()` calls that would convert the Decimals back to binary float. See `docs/MONEY_PRECISION.md`. |

To apply **only** the audit indexes — the normal case:

```
alembic -c db_migrations/alembic.ini upgrade 0002_audit_log_indexes
```

Never `alembic merge` these two to silence the error. Merging asserts they
belong on one line of history, which is exactly what is not true here. If
`0002_money_numeric` is ever cleared to run, alembic tracks the two heads
independently and no merge revision is needed.

Verified on a throwaway SQLite copy: `heads` reports both; `upgrade head` exits
non-zero; `upgrade 0001_baseline` then `upgrade 0002_audit_log_indexes` creates
all five indexes, stamps `0002_audit_log_indexes` alone, and leaves
`invoices.total` / `payments.amount` as `REAL` — the money branch is not pulled
in.

## Creating and applying a new migration

Handwritten (preferred here — see the autogenerate caveat below):

```
alembic -c db_migrations/alembic.ini revision -m "add pets.microchip_id"
# edit db_migrations/versions/<rev>_add_pets_microchip_id.py
alembic -c db_migrations/alembic.ini upgrade <rev>
```

Name the revision rather than saying `head`: there is more than one head (see
above), so `head` errors. `revision -m` also picks a parent for you — check the
generated `down_revision` is the branch you meant before applying it.

Autogenerated:

```
$env:ALEMBIC_AUTOGEN = "1"
alembic -c db_migrations/alembic.ini revision --autogenerate -m "add pets.microchip_id"
```

`ALEMBIC_AUTOGEN=1` is required because this project has **no SQLAlchemy
models**. `init_db()` in `models/database.py` is the only description of the
schema, so there is nothing for alembic to diff against. With the flag set,
`env.py` runs `init_db()` against a throwaway SQLite file and reflects it as the
target metadata. Consequences:

* The workflow is inverted from normal Alembic: you change `_SCHEMA` in
  `models/database.py` **first**, then autogenerate picks the change up.
* The reflected target is SQLite-flavoured. Autogenerating against PostgreSQL
  will report type noise (TEXT vs VARCHAR, INTEGER vs BIGINT). Trust it for
  *structural* drift — missing table, missing column, missing index — not for
  type drift. Read every generated migration before applying it.
* Without the flag, autogenerate silently produces an empty migration.

`alembic check` (same flag) is the fast "has anything drifted?" probe.

## Coexistence with `init_db()` — read this before the first deploy

`init_db()` still runs on **every** application boot (`app.py` ~line 48) and
still executes the full 55-table DDL, the ad-hoc `ALTER TABLE`s and the seed
inserts. Migrations now describe that same schema. **Both mechanisms are live at
the same time.** That is deliberate, and it is safe for now because:

* Every statement `init_db()` runs is `CREATE TABLE IF NOT EXISTS` /
  `CREATE INDEX IF NOT EXISTS`, or an `ALTER TABLE ADD COLUMN` wrapped in
  `_try_stmt()` which swallows the "already exists" failure. On an
  already-migrated database every one of them is a no-op.
* Alembic keeps its state in its own `alembic_version` table, which `init_db()`
  never touches.
* Seed data is *not* in any migration (see below), so the two cannot fight over
  rows.

It is **not** safe indefinitely. While both are live, a schema change made only
in a migration will be invisible to `_SCHEMA`, and a fresh install (which is
built by `init_db()`, not by `upgrade`) will silently lack it. **Until cutover,
every schema change must be made in both places: a new revision *and*
`_SCHEMA`.** That duplication is the cost of the transition, and the reason to
keep the transition short.

### Cutover

1. Stamp production at `0001_baseline` (above). Stamp every dev machine too.
2. Transition period: schema changes go in a revision **and** in `_SCHEMA`.
   Deploys run `alembic upgrade <rev>` before starting the app — named, not
   `head`, while the two branches above coexist.
3. Cutover: delete the `conn.executescript(_SCHEMA)` call, the ad-hoc `ALTER`
   block and `_run_pg_migrations()` from `init_db()`. Fresh installs then get
   their schema from alembic. `init_db()` keeps only the seeding. Cutover needs
   a single head, so it is blocked until `0002_money_numeric` is either applied
   or withdrawn — resolve that branch before attempting it.
4. After cutover the seed step should also be gated on a first-run check rather
   than running on every boot, but that is a separate change.

## What is in migrations and what is not

**In migrations: DDL only.** Tables, columns, indexes, constraints.

**Not in migrations: seed data.** Roles, item categories, WhatsApp templates,
the service price catalog, shifts, leave types, grooming services, boarding
rooms, budget targets, the default clinic/branch/warehouse row, and the admin
user all stay in `init_db()`.

The reason is blunt: a live clinic edits those rows. They change prices in
`service_catalog`, rename roles, rewrite WhatsApp templates. A migration that
re-seeds them would overwrite paying customers' configuration, and a `downgrade`
that deletes them would destroy it. Seeds are *initial application state*, not
schema. They belong to whatever creates a new tenant, not to a schema
version. The one exception rule: if a seed row ever becomes structurally
required (a NOT NULL FK pointing at it), that row's insert belongs in the
migration that adds the constraint — and nowhere else.

## Rollback

For an ordinary revision:

```
alembic -c db_migrations/alembic.ini downgrade -1          # back one revision
alembic -c db_migrations/alembic.ini downgrade 0001_baseline
```

**`0001_baseline` has no downgrade.** It raises deliberately. The only "down"
from the baseline is an empty database — i.e. dropping every owner, pet, visit
and invoice in the system. Restore from a backup instead.

### Warning: `downgrade` on a production database holding patient records

A downgrade is not an undo. `op.drop_column()` deletes the data in that column
permanently; `op.drop_table()` deletes the table. There is no transaction to roll
back once it commits, and on PostgreSQL DDL that has committed is gone. This
database holds clinical records — diagnoses, prescriptions, lab results,
vaccination history — which are a legal record in most jurisdictions, not just
application data.

Before any downgrade against production:

1. Take a full backup and **verify you can restore it** somewhere else.
2. Run the downgrade against a restored copy first and check the result.
3. Prefer rolling *forward* with a corrective migration. A new revision that
   fixes the mistake is almost always safer than reversing the one that made it.

## Verified behaviour

Checked end-to-end against throwaway SQLite files (never `data/platform.db`):

* `alembic upgrade 0001_baseline` on an empty database produces 73 tables — the
  identical set of tables, indexes and columns that `init_db()` produces, with
  zero differences reported by `compare_metadata` (including server defaults).
  (Recorded as `upgrade head` before the second branch existed; `head` is now
  ambiguous and errors.)
* `alembic stamp 0001_baseline` on an `init_db()`-built database changed no
  schema object and left the version row `0001_baseline`.
* `alembic check` reports no operations against either database.
* `alembic heads` reports both `0002_audit_log_indexes` and
  `0002_money_numeric`; `upgrade head` exits non-zero with "Multiple head
  revisions"; `upgrade 0002_audit_log_indexes` from the baseline creates the
  five `audit_log` indexes, stamps that revision alone, and leaves
  `invoices.total` and `payments.amount` as `REAL` — the money branch is not
  pulled in.
